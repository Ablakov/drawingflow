# Архитектура DrawingFlow

Документ описывает фактическое состояние системы после этапов 1–5 и принятые архитектурные решения.
Язык интерфейса и документации — русский; идентификаторы в коде, БД и API — английские.

## 1. Назначение

DrawingFlow — система централизованного управления проектной (строительной и инженерной) документацией:
единый сервер компании, PostgreSQL, центральное хранилище файлов, неизменяемые версии документов,
маршруты согласования и автоматический мониторинг рабочих папок на рабочих станциях.

Основной пользовательский интерфейс — **нативное Windows-приложение (WPF)**. Браузерный интерфейс не предусмотрен.

## 2. Компоненты

| Проект | Тип | Назначение |
|---|---|---|
| `DrawingFlow.Desktop` | WPF, `net10.0-windows` | Рабочее место сотрудника: вход, выбор организации, проекты, участники, журнал аудита, администрирование, настройки. |
| `DrawingFlow.Server` | ASP.NET Core Web API | Единственная точка доступа к данным: аутентификация, авторизация, организации/проекты/участники, документы и версии, согласование, агенты, аудит, health-checks. |
| `DrawingFlow.Agent` | .NET Worker Service (служба Windows) | Наблюдение за папками, устойчивая очередь SQLite, стабильность файлов, SHA-256, сопоставление с документами, загрузка версий с идемпотентностью, отчёты и сердцебиение. |
| `DrawingFlow.Domain` | библиотека | Сущности, перечисления, правила доступа (`AccessRules`), доменные исключения. Не зависит от EF Core, HTTP и WPF. |
| `DrawingFlow.Application` | библиотека | Сценарии использования (сервисы), абстракции инфраструктуры (`IAppDbContext`, `IClock`, `IPasswordHasher`, `ITokenService`, `ICurrentUser`), маппинг в контракты. |
| `DrawingFlow.Infrastructure` | библиотека | EF Core + Npgsql (`AppDbContext`, конфигурации, миграции), JWT, хеширование паролей, инициализация БД, файловое хранилище версий. |
| `DrawingFlow.Contracts` | библиотека | DTO и запросы HTTP API. Общая для сервера и клиентов, без зависимостей от домена. |
| `DrawingFlow.Client` | библиотека | Типизированный HTTP-клиент API с хранением сессии и прозрачным продлением токенов. Используется Desktop и Agent. |
| `tests/DrawingFlow.UnitTests` | xUnit | Правила доступа, валидация, сущности, JWT, хеширование, HTTP-клиент. |
| `tests/DrawingFlow.IntegrationTests` | xUnit + `WebApplicationFactory` + PostgreSQL | Сквозные сценарии API на настоящей базе данных. |

Два проекта (`Contracts`, `Client`) добавлены к структуре из технического задания осознанно:
клиенты не должны ссылаться на серверные сборки (`Application`, `Infrastructure`), а дублировать DTO и HTTP-код в Desktop и Agent недопустимо.

### Зависимости между проектами

```
Desktop ──► Client ──► Contracts
Agent   ──► Client ──► Contracts
Server  ──► Application ──► Domain
        └─► Infrastructure ──► Application
Application ──► Contracts (только для маппинга и DTO)
```

Домен не знает о контрактах; перечисления контрактов повторяют доменные и проверяются тестом на паритет (`EnumParityTests`).

## 3. Серверная часть

### 3.1. Слои

* **Контроллеры** (`Server/Controllers`) — тонкие: разбор запроса, вызов сервиса, код ответа.
* **Сервисы приложения** (`Application/*Service.cs`) — транзакционные сценарии. Каждый сценарий начинается с проверки прав через `AccessService`,
  изменяет сущности, пишет запись аудита и один раз вызывает `SaveChangesAsync` (одна транзакция на операцию).
* **Домен** — инварианты сущностей (фабрики `Create`, методы изменения состояния, `Guard`-проверки с русскими сообщениями).
* **Инфраструктура** — PostgreSQL через EF Core 10; перевод ошибок СУБД (уникальность, конкурентное изменение) в `ConflictException`.

### 3.2. Аутентификация

* Пароли: `PasswordHasher<T>` из ASP.NET Core Identity (PBKDF2-HMAC-SHA512, формат V3). Полный стек Identity (UserManager, cookie) не используется:
  клиентам (Desktop, служба Agent) нужны токены, а не cookie-сессии — это обоснованная альтернатива по п. 2 ТЗ.
* Access-токен: JWT HS256, срок жизни по умолчанию 60 минут, утверждения `sub`, `login`, `display_name`, `server_admin`, `principal_type`.
* Refresh-токен: случайные 256 бит, в БД хранится только SHA-256; при обновлении токен ротируется, повторное предъявление уже обменянного токена отзывает все сессии пользователя.
* Ограничение частоты входа: политика `login` (по умолчанию 20 попыток в минуту с одного адреса).

### 3.3. Авторизация

Роли организации: `Owner`, `OrganizationAdmin`, `Member`. Роли проекта: `ProjectManager`, `Engineer`, `Reviewer`, `Viewer`.
Владелец и администратор организации действуют как руководители всех её проектов; администратор сервера (`IsServerAdministrator`) — как владелец любой организации.

Права вычисляются только на сервере (`Domain/Authorization/AccessRules.cs`) и возвращаются клиенту в DTO (`permissions: ["View", "ManageMembers", …]`).
Desktop лишь отражает их (скрывает кнопки); любое действие повторно проверяется сервером.
Отсутствие доступа к организации или проекту маскируется ответом **404**, чтобы не раскрывать существование чужих объектов (защита от IDOR).

### 3.4. Модель ошибок

Все ошибки — `application/problem+json` (RFC 9457) с русским `title`/`detail` и расширениями `errorCode`, `traceId`, `errors` (для валидации).

| Исключение домена | HTTP |
|---|---|
| `ValidationException` | 400 |
| `UnauthorizedException` | 401 |
| `ForbiddenException` | 403 |
| `NotFoundException` | 404 |
| `ConflictException` | 409 |
| `DomainRuleException` | 422 |

Непредвиденные ошибки → 500 без внутренних деталей (детали — в журнале сервера).

### 3.5. Документы и версии (этап 2)

* `Document` — стабильная идентичность (шифр уникален в проекте, не зависит от имени файла); `DocumentVersion` — неизменяемая запись о содержимом.
* Загрузка версии (`POST /api/documents/{id}/versions`, тело — поток файла, параметры в строке запроса):
  1. проверка прав `UploadVersions` и статуса документа (архив запрещает загрузку);
  2. быстрый ответ по ключу идемпотентности, если версия уже создана;
  3. потоковая запись в `IFileStorage` с подсчётом размера и SHA-256, лимит размера (`Storage:MaxFileSizeBytes`); при несовпадении с заявленным хешем файл удаляется, ответ 400;
  4. транзакция: `SELECT … FOR UPDATE` строки документа → повторная проверка ключа идемпотентности → номер версии = max + 1 → INSERT версии → UPDATE указателя текущей версии и статуса (`InProgress`) → запись аудита → COMMIT;
  5. при любой ошибке объект хранилища удаляется.
  Уникальные индексы (DocumentId, VersionNumber) и (DocumentId, IdempotencyKey) — страховка на уровне СУБД.
* Новая версия никогда не наследует согласование: документ в любом статусе (кроме архива) возвращается в «В работе».
* Скачивание (`GET …/versions/{versionId}/content`) — только после проверки `View`; ответ с `Content-Disposition` (имя файла в UTF-8), заголовками `X-DrawingFlow-Sha256`/`X-DrawingFlow-Version` и поддержкой диапазонов. Факт скачивания попадает в аудит.
* Изменение метаданных документа защищено оптимистичной блокировкой (`xmin` → `RowVersion` в DTO; расхождение → 409).
* `IFileStorage` — абстракция хранилища (файловая реализация `FileSystemStorage`: временный файл → атомарное перемещение, проверка ключей и запрет выхода за корневой каталог; объекты никогда не перезаписываются). S3-совместимая реализация добавляется без изменений в Application.
* Отказ хранилища (нет записи, отсутствует объект) → 503 `storage_unavailable`; метаданные остаются доступны.

### 3.6. Согласование (этап 4)

* Решение (`Review`) всегда относится к конкретной версии; статусы документа и версии меняются только командами домена
  (`SubmitForReview`, `Approve`, `RequestRevision`, `Release`) по таблице переходов `DocumentWorkflow`.
* Модель решения одиночная: первое решение назначенного проверяющего или руководителя проекта определяет исход, задачи остальных проверяющих закрываются.
  Руководитель проекта (и администратор организации) может решать без назначения.
* Возврат на доработку требует комментария и ставит автору версии (или отправителю) задачу `Rework`.
* Загрузка новой версии сбрасывает согласование: документ — «В работе», непроверенная предыдущая версия — `Superseded`, открытые задачи отменяются;
  согласованные и выпущенные версии остаются в истории со своим статусом.
* Доступные действия (`AvailableActions`) вычисляет сервер по статусу, правам и назначению; Desktop лишь показывает соответствующие кнопки.
* Кандидаты в проверяющие: участники проекта с ролями «Проверяющий»/«Руководитель проекта» и администраторы организации.

## 4. Desktop (WPF)

* MVVM на CommunityToolkit.Mvvm, DI на `Microsoft.Extensions.Hosting`.
* `ShellCoordinator` управляет окнами: вход → главное окно → выход/истечение сессии → вход.
* `ShellViewModel` — пользователь, выбор организации, навигация (список страниц зависит от прав), строка состояния соединения.
* Страницы (`PageViewModelBase.LoadAsync`): Главная (в т. ч. недавние изменения документов), Проекты (поиск, фильтр, серверная сортировка и пагинация), Проект (карточка, участники),
  Документы (реестр выбранного проекта: поиск по шифру и наименованию, фильтры по статусу и разделу, пагинация), Документ (метаданные, история версий,
  загрузка новой версии с локальным SHA-256 и прогрессом, скачивание, открытие в связанном приложении, показ в Проводнике, сравнение метаданных версий),
  Задачи (мои согласования и задачи на доработку с решениями из списка), Участники организации, Журнал аудита, Агенты (администраторы: регистрация, отзыв, папки наблюдения),
  Синхронизация (очередь операций агентов с действиями «Повторить», «Сопоставить», «Отклонить»), Администрирование (организации и пользователи сервера), Настройки.
  Карточка документа содержит блок «Согласование»: состояние, доступные действия, открытые задачи и история решений. На главной — сводки согласования и синхронизации.
* Локальные копии версий хранятся в `%LOCALAPPDATA%\DrawingFlow\cache\{документ}\v{N}\` и перед открытием сверяются по SHA-256.
* Диалоги — модели `DialogViewModelBase` в общем окне `DialogWindow`; формы — `UserControl` через `DataTemplate`.
* Все вызовы API асинхронные; `ViewModelBase.RunAsync` единообразно показывает занятость и ошибки (нет соединения, отказ сервера, валидация).
* Сессия хранится в `%LOCALAPPDATA%\DrawingFlow\session.bin`, зашифрованной DPAPI (область текущего пользователя); настройки — `%APPDATA%\DrawingFlow\settings.json`.
* Адрес сервера без TLS допускается только для loopback (локальная разработка).

Проект собирается на macOS/Linux благодаря `EnableWindowsTargeting` (проверено), но **запускается только на Windows**.

## 5. Agent

Служба Windows (`UseWindowsService`), работающая независимо от Desktop. Подробное описание — в `file-sync.md`. Ключевые решения:

* **Второй тип субъекта на сервере.** Агент аутентифицируется индивидуальным ключом установки (хранится хешем), получает JWT с `principal_type = agent`;
  `ICurrentUser` различает пользователя и агента, `AccessService` ограничивает агента проектами его включённых папок. Отзыв ключа проверяется на каждом запросе (`AgentRevocationMiddleware`).
* **Истина — на диске и на сервере, а не в событиях.** `FileSystemWatcher` даёт подсказки, периодическая сверка находит пропущенное; `FileStates` отсекают ложные изменения по хешу.
* **Идемпотентность сквозная.** Идентификатор локальной операции = ключ идемпотентности загрузки = идентификатор серверной операции; повтор после сбоя не создаёт дубликатов.
* **Решения пользователя доставляются агенту через сервер.** Пользователь в Desktop выбирает документ/повтор/отклонение, сервер хранит запрошенное действие, агент забирает его при отчёте или сердцебиении.
* **Тестируемость.** Ядро (`SyncEngine`) не содержит таймеров: шаги вызываются явно, часы абстрагированы; интеграционные тесты гоняют настоящее ядро с настоящей файловой системой против тестового сервера.
* Регистрация агента: `DrawingFlow.Agent register --server … --key …` сохраняет ключ (DPAPI, область компьютера); в режиме разработки на macOS/Linux — файл 0600.

### 5а. Эксплуатационные функции (этап 5)

* `/health/ready` проверяет базу данных и запись в хранилище (пробный файл); `/health/live` — только процесс.
* `DrawingFlow.Server --verify-storage` сверяет версии с объектами хранилища без изменений данных.
* Режим обратного прокси (`ReverseProxy`) с перечнем доверенных прокси; без него заголовки `X-Forwarded-*` игнорируются.
* Временные пароли: признак `MustChangePassword` в токене, `PasswordChangeRequiredMiddleware` на сервере, обязательный диалог в Desktop.
* Файловые журналы Desktop и агента (`DrawingFlow.Client.Logging.FileLoggerProvider`), журнал событий Windows для службы агента.
* Скрипты `scripts/backup.sh` и `scripts/restore.sh` (см. `backup-recovery.md`).

## 6. Конфигурация

Все параметры — через `appsettings*.json`, переменные окружения (`Section__Key`) или аргументы. Ключевые разделы сервера:
`ConnectionStrings:DrawingFlow`, `Database:MigrateOnStartup`, `Jwt:*`, `Bootstrap:Administrator:*`, `RateLimits:LoginPerMinute`, `Storage:RootPath`, `Storage:MaxFileSizeBytes`, `ReverseProxy:*`, `Kestrel:*`.
Строка подключения читается при создании контекста данных, поэтому её можно задавать любым источником конфигурации.

## 7. Принятые решения и допущения

1. **Один сервер — модульный монолит.** Микросервисы не нужны для целевой нагрузки; слои разделены проектами.
2. **Идентификаторы** — `Guid` версии 7 (монотонные, дружественные индексам PostgreSQL).
3. **Перечисления в БД** — строками (читаемость, устойчивость к перенумерации).
4. **Время** — только UTC (`timestamp with time zone`); клиент переводит в местное.
5. **Имена объектов БД** — PascalCase по умолчанию EF Core.
6. **Поиск** — `lower(...)`/`contains` на стороне СУБД; база должна быть создана с UTF-8-локалью, поддерживающей кириллицу (см. `installation.md`).
7. **Один участник не может быть добавлен в проект, если он не состоит в организации.** Удаление из организации снимает роли во всех её проектах.
8. **Последний владелец организации не может быть понижен или удалён.**
9. **Удаление организаций, проектов, документов и версий не предусмотрено** — только архивирование/деактивация (историю удалять нельзя).
10. **Загрузка — «сырой» поток, а не multipart.** Параметры передаются в строке запроса; это упрощает потоковую запись без буферизации и подходит агенту.
11. **Ключи сущностей задаёт домен (Guid v7)**, поэтому новые сущности всегда добавляются в контекст явно (`Add`), иначе EF считает их существующими.

## 8. Известные ограничения этапов 1–5

* Desktop проверен компиляцией и тестами моделей/клиента; визуальная проверка на Windows не выполнялась (см. `roadmap.md`).
* Нет оптимистичной блокировки при редактировании метаданных проекта (последняя запись побеждает); для документов она реализована (`RowVersion`).
* Сравнение версий — только по метаданным (размер, хеш, автор, дата, комментарий); сравнение содержимого чертежей не заявлено.
* Загрузка больших файлов не возобновляется после обрыва: повтор с тем же ключом идемпотентности начинает передачу заново. Многочастная загрузка появится, если её потребуют реальные размеры файлов.
* Антивирусная проверка — точка расширения в конвейере загрузки, реализация отсутствует.
* Настройка папок наблюдения в Desktop доступна администраторам организации (страница «Агенты»); API разрешает это и инженерам проекта.
* Согласование — одиночное решение; параллельное согласование несколькими проверяющими с кворумом не реализовано (все назначенные видят задачу, решает первый).
* Уведомления (почта, всплывающие сообщения) о новых задачах отсутствуют; задачи видны на главной и странице «Задачи».
* Наблюдатель файловой системы агента не покрыт автотестами (зависит от ОС); сверка и конвейер — покрыты.
* Desktop и служба агента на Windows не запускались на машине разработки; порядок ручной проверки — `windows-verification.md`.
